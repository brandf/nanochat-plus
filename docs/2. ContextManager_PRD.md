# Product Requirements Document (PRD)
## Project: Dynamic WorkingContext (WC) Manager for Long-Context LLM with Multi-LOD Gist Tree

---

## 1. Overview

This PRD defines the **Context Manager Add-On** responsible for dynamically selecting and maintaining a *WorkingContext (WC)*—a sparse, zoomable subset of a large *MegaContext (MC)* stored on disk. It now acts as the façade that owns every tree-oriented runtime structure:

- **MegaContextTree (MCT)**: in-memory owner of the dense multi-LOD tensors plus incremental gist building.
- **WorkingContextTree (WCT)**: flattened, transformer-ready sparse slice derived from the MCT.
- **LensNet (future)**: learned routing head that will eventually provide focus scores.

All other components talk to the Context Manager rather than juggling these modules separately.

- **MegaContext (MC)**: full multi-LOD tree over a very long sequence (e.g. 1M tokens). Potentially stored on disk; only random-access queries to individual nodes (e.g. “load children of node X”) are allowed. No global traversals or sweeps over MC are permitted.
- **WorkingContext (WC)**: a sparse subset of MC nodes (tokens + gists at multiple LODs) held in memory and passed through the transformer at each decode step.

The WC Manager’s job is to:

- Maintain WC length below a fixed budget `WC_len` (e.g. 64k nodes) while the true MegaContext length (`MC_len`) can be up to millions of tokens.
- Dynamically **expand** or **collapse** leaf nodes based solely on information available in WC:
  - Expand: bring in one or more/all children of a gist node from MC into WC.
  - Collapse: remove less-useful leaf nodes from WC.
- Respect strict **tree validity constraints**:
  - Parents are **never removed** while any of their children are in WC.
  - Only **leaf nodes** may be removed or expanded.

The context manager does **not** change the model architecture; it only manages which nodes from the global tree are visible to the transformer at any given step.

## 2. Goals and Non-Goals

### 2.1 Goals

1. **Dynamic WC Maintenance**
   - Keep WC as a valid sparse subtree of MC under a hard budget `WC_len`.
   - Update WC and MC incrementally as new tokens are generated (autoregressive decoding).

2. **Attention-Driven Focusing**
   - Use only **attention patterns within WC** (from the base transformer) to estimate per-node “focus scores”.
   - Make expand/collapse decisions based on those scores and simple heuristics.

3. **Hierarchical Safety**
   - Guarantee that:
     - Parents cannot be removed if any child is in WC.
     - Only leaf nodes can be removed (collapsed) or expanded.
   - Support partial expansion: expanding a gist node may bring in a **subset** of its children (even one at a time).

4. **Must-Keep Coverage**
   - Always keep:
     - The last `K` LOD0 token nodes (short-range detailed context).
     - The last node at each LOD (coarse summaries of the far past).
   - Optionally keep designated anchor nodes (e.g. system prompts).

5. **Local and Disk-Friendly**
   - All scoring / decision logic must operate in **O(WC_len)** time per step.
   - Access MC only via explicit random-access calls to fetch children of specific nodes; no full MC traversal.

6. **Future-Proofing**
   - Provide hooks that can later be used for a learned “LensNet” scorer without changing core piping.
   - Make the design agnostic to the exact tree structure and GistNet implementation, as long as parent/child relationships are well-defined.

### 2.2 Non-Goals

- No policy gradient / RL training for context selection in this POC.
- No teacher distillation or oracle-based “ideal context” labels.
- No optimization for the MC storage format itself (assume a simple API).
- No requirement to achieve provably optimal context selection—this is a **heuristic, engineering-friendly zooming mechanism**.
- No global operations over MC (no scans over all nodes on disk).
- The context manager does **not** change the model architecture; it only manages which nodes from the global tree are visible to the transformer at any given step.

### 2.3 Context-Manager Variants

- **TrainingContextManager (TCM)** acts as the training-time façade. It ingests full token batches, embeds them, builds a MegaContextTree, and materializes a WorkingContextTree that is both `tree_causal_ordering` and `fully_virtual` so gradients flow through every node. TCM keeps `WCT.max_nodes` equal to the full tree (zero sparsity), applies deterministic (seeded) masked removals over eligible leaves for augmentation, and owns the LensNet routing head for supervision (even though LensNet is not yet used for selection).
- **InferenceContextManager (ICM)** is the runtime façade. It persists MCT + WCT across autoregressive steps, appends new LOD0 embeddings to the MCT each step, mirrors newly created latents into the WCT, and maintains the live WCT size inside a configurable window `[target_node_count - target_node_shrink, target_node_count + target_node_growth]` (which must be ≤ `max_nodes`). Once LensNet is implemented, ICM will ask it for focus scores; until then it emits **seeded deterministic** pseudo-random scores in `[-1, +1]` per node so behavior is reproducible while still respecting every WCT sparsity invariant (parents remain whenever children are present, aside from partial tail blocks).

Both managers own MCT/WCT/LensNet instances internally so downstream modules only talk to the façade.

## 3. User Stories

1. **As a model**, I want WC to contain the most relevant parts of the long history so I can accurately predict the next token without reading the entire MegaContext.
2. **As a researcher**, I want the context selection mechanism to be interpretable and easy to modify so I can experiment with different zooming policies and learned scoring functions.
3. **As an engineer**, I want context management to be a separate, well-defined module that plugs into the existing multi-LOD tree transformer without invasive changes.

## 4. Functional Requirements

### 4.0 Ownership & Interfaces

- Both TCM and ICM receive token batches or token embeddings plus configuration.
- Each manager **owns**:
  - A MegaContextTree that holds the full multi-LOD tensors and incremental gist builder.
  - A WorkingContextTree that exposes flattened nodes to the transformer.
  - LensNet (future) or, until LensNet is ready, a seeded deterministic placeholder scorer that outputs pseudo-random values in `[-1, +1]` per node.
- External modules interact only with the Context Manager façade; they never manipulate MCT/WCT directly.

### 4.1 Inputs

Per decode step, the context manager receives:

- **WC state**:
  - The current list of WC nodes with metadata:
    - `id` (MC node ID).
    - `level` (LOD index, 0 for tokens).
    - `mu`, `sigma` (time and scale).
    - `parent` (MC node ID or `None`).
    - `children_in_WC` (list of child IDs that are currently in WC).
    - `has_children_in_MC`: boolean flag indicating whether this node has children that can be fetched from MC.
    - `is_must_keep`: boolean indicating whether this node is part of the must-keep set (tail window, last per LOD, etc.).
- **MC access API**:
  - An interface that supports:
    - `load_children(mc_node_id) -> List[MCNodeMetadata]`  
      Returning at least: child ID(s), level, mu, sigma, and latent(s).
- **Attention maps from the last transformer forward** on the current WC:
  - Typically a tensor `[num_layers, num_heads, Q, K]` where Q and K index WC nodes.
- **WC configuration**:
  - `WC_len`: maximum allowed size for WC.
  - `tail_token_keep`: number of LOD0 tokens at the tail that must always be kept.
  - `must_keep_levels`: whether to always keep the latest node at each LOD level.
  - Optional knobs for expansion and collapse aggressiveness.

### 4.2 Outputs

- **Updated WC state**:
  - New list (or mapping) of WC nodes after expansion and collapse.
  - All invariants satisfied (see below).
- **Operation log (optional)**:
  - A list of actions taken during this step, e.g.:
    - `expand(node_id=X, child_id=Y)`
    - `collapse(node_id=Z)`
  - Useful for debugging and analysis.

### 4.3 TrainingContextManager (TCM) Workflow

- **Batch ingest:** Accepts a `[B, T]` (or `[B, T, d_model]`) batch, runs embeddings, and streams the result through MegaContextTree so every LOD is built in a single batched pass.
- **Working view build:** Converts the full MCT into a WorkingContextTree with `tree_causal_ordering=True` and `fully_virtual=True`. `WCT.max_nodes` equals the total number of nodes in the MCT, so no structural sparsity exists at build time.
- **Masked sparsification:** Applies deterministic (seeded) masked removals (marking `WCTFlags.MASKED`) over eligible leaf nodes to simulate inference sparsity while keeping tensors compile-friendly. Tail tokens + last-per-LOD nodes remain active, and these masks **replace** any attention-dropout mechanism in the transformer (keep dropout probability at zero so only structural masks gate activations).
- **Holdout mask:** Builds a deterministic mask over the tail-induced subtree that remains active so it can provide ground-truth targets for next-gist prediction. This mask composes with the masked-removal mask prior to the transformer forward.
- **LensNet supervision:** Once LensNet is implemented, the TCM is responsible for computing the attention-derived signed targets described in `docs/3.*` and updating LensNet weights. Until then it records the per-node statistics needed for future validation (attention summaries, sampled leaf masks, etc.).
- **Implementation note:** the short-term training implementation stays entirely in the fully-masked regime (no physical omissions/reorders). This keeps the mirror step a fused tensor op and makes torch.compile happy; the richer omit/rebuild path described elsewhere remains the plan of record.

### 4.4 InferenceContextManager (ICM) Workflow

- **Initialization:** Starts from an empty MCT or one populated by a system prompt. WCT initially mirrors this state with `tree_causal_ordering=True`.
- **Autoregressive step handling:**
  - New LOD0 embeddings are appended to the MCT every decode step; the tree incrementally materializes completed gist blocks.
  - WCT receives the new token latents plus any newly created gists so the transformer can consume them immediately.
- **Size window management:**
  - Config knobs:
    - `target_node_count`: desired steady-state WCT length.
    - `target_node_growth`: allowed overflow before a refocus triggers.
    - `target_node_shrink`: collapse depth during refocus before re-expanding.
  - The enforced window `[target_node_count - target_node_shrink, target_node_count + target_node_growth]` must be ≤ `WCT.max_nodes`.
  - When the window is violated (typically on overflow), the ICM runs a refocus pass that collapses to/below `target_node_count - target_node_shrink`, then expands prioritized nodes back up to `target_node_count`.
- **Focus scores:** Until LensNet exists, the ICM uses a seeded random score generator that outputs values in `[-1, +1]` per node per refocus call. These placeholder scores only prioritize eligible leaves—the expand/collapse logic still enforces the ancestor invariants above. Once LensNet is available, that module plugs into the same hook.
- **Batch discipline:** Appends are always synchronized across the batch; the ICM rejects per-sequence appends to keep block alignment intact.
- **Attention dropout interplay:** The structural masks produced by WCT (masked removals, holdouts, focus-driven pruning) are the *only* masking mechanism applied to the transformer. Keep built-in attention dropout disabled both during training and inference so these masks remain deterministic and ancestor-safe.

## 5. Behavioral Requirements

### 5.1 Node Validity Rules

1. **Parent-presence rule**  
   If a node is in WC and has a parent in MC, that parent **must also** be in WC.  
   Corollary: A parent node that has one or more children present in WC cannot be removed.

2. **Leaf-only modification rule**  
   - **Collapse** operations:
     - May only remove **leaf nodes** (nodes with no children currently in WC).
   - **Expand** operations:
     - May only be applied to leaf nodes (nodes with no children currently in WC) that have children in MC.
     - Expansion adds children without removing the parent.

3. **Induced subtree invariant**  
   At all times, the set of nodes in WC must form an **induced subtree** of the underlying MC tree:
   - If a node is present, all ancestors along its path to the root are present.
   - No “dangling” children without parents.

4. **Must-keep nodes cannot be removed**  
   - Nodes flagged as `is_must_keep` (e.g., last K tokens, last node per LOD) are never removed by the context manager.
5. **Tail-block exemption**  
   - The only time a node may exist without a parent is during the partial tail block while waiting for enough children to form a full gist; once a parent exists, the parent-presence rule applies again.

### 5.2 Focus Scoring

The context manager must estimate an **importance / focus score** for each node in WC using only:

- Attention maps from the last forward pass.
- Node metadata available in WC (`level`, `mu`, `sigma`, recency, etc.).

Core requirement:

- Define a function:
  - `focus_k = f(attention_maps, node_metadata_k)`  
  that yields a scalar focus score for each node `k` in WC.

Initial POC requirement:

- At minimum, `focus_k` should incorporate:
  - The average attention weight received by node `k` from a small set of “tail” query positions (e.g., last 1–4 token nodes) over all layers and heads.
- Optionally apply:
  - Exponential moving average over time.
  - Level-dependent normalization.

No computation may involve nodes not in WC.

### 5.3 Candidate Selection: Expand vs Collapse

#### Expand Candidates

A node is eligible to be considered for expansion if:

- It is in WC.
- It is a leaf node (no children currently in WC).
- Its `has_children_in_MC == True` (it has children stored in MC).

Expansion behavior:

- Expansion never removes the parent.
- Expansion may bring in:
  - All children, or
  - A subset of children (at least one), e.g., one at a time.

The POC should support both strategies but may default to expanding **one child at a time** for fine-grained control.

#### Collapse Candidates

A node is eligible for collapse if:

- It is in WC.
- It is a leaf node (no children currently in WC).
- It is **not** `is_must_keep`.

Collapse behavior:

- Removing a leaf node from WC.
- Parent remains.

### 5.4 Scoring Functions

The PRD does not prescribe exact formulas but requires:

- An `expand_score(node)` that increases when:
  - `focus(node)` is high.
  - Node is at a coarse LOD (high-level gist).
  - Node is not too recent (so that detail elsewhere is preferred).
- A `collapse_score(node)` that increases when:
  - `focus(node)` is low.
  - Node is at a fine LOD (detail) whose parent is available as a summary.
  - Node is not in the tail or must-keep set.

Implementation details go into the TDD, but they must satisfy:

- Fully computed in terms of WC nodes only.
- Executable in O(WC_len).

### 5.5 Update Loop

At each decoding step:

1. **Compute focus scores** for all WC nodes from attention + metadata.
2. **Identify must-keep nodes** (enforce `is_must_keep` flags).
3. **If WC size > WC_len**:
   - Prefer collapse operations on low-focus leaf nodes, respecting constraints, until `WC_len` is satisfied.
4. **If WC size < WC_len**:
   - Consider expand operations on high-focus leaf nodes that have children in MC, until:
     - `WC_len` is reached, or
     - No expand candidate has positive benefit.

Operations must be applied incrementally (one expand/collapse at a time), updating WC state as they go.
Note that just because WC size > WC_len doesn't me we should never expand.  We will often want to expand one portion of the WC even if it means we now need to collapse more nodes to end up at WC_len.

---

## 6. Performance Requirements

- The context manager must run in O(WC_len) time per step, ignoring disk I/O for expansions.
- Number of disk accesses per step:
  - Should be bounded by a small constant or small multiple of the number of expansions.
  - No bulk scans.
- Memory:
  - WCNode objects and associated metadata must fit within the existing model’s memory budget for `WC_len` nodes.

   - `focus_score.py`: focus scoring based on attention.

3. **Tests**
   - Unit tests for WCState invariants.
   - Unit tests for focus scoring.
   - Integration tests on small synthetic trees.
